1. The big picture

There is a native Swift layer inside the iOS app target that iOS can wake up without launching the React Native app. It reads a small SQLite table that TypeScript keeps up to date. When the user wants to see full results, Swift leaves a note in UserDefaults, opens the app, and React Native reads the note and fills the Search tab.

2. The six words that matter

App IntentSwift A struct conforming to AppIntent: a title, some @Parameters, and a perform(). It is a verb the system can call. Think: one Redux action type with a handler, registered with iOS at build time.
App EntitySwift A struct conforming to AppEntity: a noun Siri can name, with an id and a query that resolves ids back to values. Ours: AssistantBookEntity, AssistantAuthorEntity.
App ShortcutiOS A phrase bound to an intent, declared in AppShortcutsProvider. This is what lets a user say a sentence with no setup. Phrases must contain \(.applicationName).
SnippetiOS The SwiftUI card Siri draws under its reply. Static unless produced by a SnippetIntent (iOS 26+). See §5.
Assistant SchemaiOS Apple-defined intent shapes (.books.playAudiobook, .system.searchInApp). Adopting one lets Siri route natural language without our phrase list.
Metadata extractioniOS A build step that scans Swift for intents/entities/shortcuts and writes Metadata.appintents/ into the .app. Siri reads that, not your running code. If it's not in the metadata, Siri doesn't know it exists.
Key mental shift from RN: nothing here is registered at runtime. There is no Siri.register(...). Types exist in the binary → the compiler extracts them → iOS indexes the app's capabilities at install. That's why a new install (not a JS reload) is required for any change in this layer, and why @available annotations end up in the metadata as "this intent exists on iOS ≥ X".

3. Why phrasing matters: two different doors

You noticed search works "if I phrase it just right." That's because there are two unrelated ways a sentence containing "search" can reach us, and they land in different code.

DoorWho owns the grammarOur code that runsResultMin iOS
AUs (AssistantShortcuts.swift)SearchLibraryIntent, SearchBooksByAuthorNameIntent (free-text follow-up)Spoken reply + card; app stays closed unless no results (then offers to open Search)26 (interactive card)
BAppleShowAssistantInAppSearchIntent (17.4–26), SearchInAppSchemaIntent (27+)App opens on Search tab17.4
Practical consequence: Door A phrases cannot include the author or title in the same sentence, and they must not start with “Search”. That shape is Door B (“Search Tim Ferriss in LAABS Audio”), and a competing shortcut lets Siri hear “books by” as “bookmark”. Door A uses Find / Look up, then asks a follow-up and searches the whole open library. If Door A finds nothing, Siri offers to open the Search tab with that text.

4. Where the data lives

Siri can invoke our intent when the app process isn't running. So the intent can't call into JavaScript, React Query, or Zustand. It needs data that is already on disk in a shape Swift can read without help.

Why the "runtime context" exists

Swift has no idea who is logged in. So whenever auth state changes, TypeScript calls AssistantBridgeModule.publishRuntimeContext({ dbPath, userId, libraryId, accessMode, canAttemptStreaming }). Swift persists that to UserDefaults and every intent reads it first. If userId is nil, Siri says sign-in is required; if libraryId is nil, it says choose a library. This is the trust boundary: the intent never guesses identity.

What "search" means in SQL

The query text is normalized (lowercase, diacritics stripped, punctuation removed) and every token must be a word prefix in search_text, which concatenates title, subtitle, author, series, and narrator. So "steph king" matches Stephen King, but "tephen" does not. Author lookups match the combined credit string ("Stephen King, Owen King" is one credit, not two people).

5. Interactive result cards: the SnippetIntent rule

This was the hardest lesson on this branch and it is worth a picture.

Think of the snippet intent as a "render intent." It carries its inputs as @Parameters (heading, books: [AssistantBookEntity], totalCount, query) — that's why AssistantBookEntity must be resolvable by id: Siri may rehydrate the card later from those ids. This requirement is also why the iOS floor moved to 17.4: AppShortcutsProvider only allows if #available(iOS 26.0, *) around shortcuts when the deployment target is ≥ 17.4.

6. From Siri into the React Native Search tab

Three things can open the app with a search in hand: Door B, the Show all results button, or a cold launch after either. They all use the same one-shot note pattern.

Why the note is bound to userId + libraryId: the intent ran against whatever context was published at that moment. If the app comes up under a different account or library (session switch, remembered session), the results would be wrong, so the note is thrown away rather than shown.

7. Scope: the Active Library rule (changed 2026-09-22)

Stored
Every audiobook library the signed-in identity has cached. Nothing was removed from the table.
Read by Siri
Only rows where library_id = context.libraryId: search, author lists, play-by-name, Suggested books, Spotlight index.
Not narrowed
Opening/playing a specific book by id (a card button, a Spotlight hit) and Resume. These already know exactly which book.

Consequences worth remembering: a book that lives only in another library now gets "I couldn't find…"; switching libraries in the app republishes the context and re-indexes Suggested books + Spotlight; a podcast library active means audiobook search returns nothing (the catalog has no podcasts).

9. How to describe a bug to me

These distinctions let me go straight to the right file:

Say thisInstead ofBecause
"The phrase X didn't match" / "Siri said the app doesn't support…""Siri didn't understand"Phrase matching is AssistantShortcuts.swift + metadata; a different problem from a wrong answer.
"It went through Door B (opened the app) when I expected a card""It opened the app"Tells me routing chose the system in-app-search intent, which is Apple's grammar, not ours.
"The dialog said … but the snippet showed …""The results were wrong"Spoken text and card come from the same outcome but different code paths (AssistantSearchCopy vs AssistantSnippetViews).
"The Show all button landed on Home / had no text""Search didn't work in the app"That's the pending-search handoff (§6): discard vs navigate, or setText timing.
"Wrong library" / "wrong user""Wrong results"Points at the runtime context or the discard branch rather than SQL matching.
"Cold launch vs warm"—Cold means RN wasn't running when the intent fired; the wait branch and startup order matter only there.
"Which iOS and which build (commit)"—Intents are baked into the binary at build time; a JS reload does not pick up Swift changes.
Things that look like bugs but are platform behavior: a card whose buttons do nothing on iOS 17–25 (no SnippetIntent there); "Search <term> in LAABS Audio" always opening the app (Door B); no cover art on cards when the book has no local cover_path; needing to reinstall (not reload) after Swift changes.
