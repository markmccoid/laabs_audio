# `react-native-continued-task` for background on-device ASR

Research date: 2026-09-10. Scope: whether `react-native-continued-task` materially improves LAABS Audio's transcription behavior when the app is backgrounded or the screen is locked. Primary sources only: Apple and Android documentation, the package's own README/source/device report, and this repository's implementation. No app behavior changed.

## Conclusion

**Yes—on iOS 26, the underlying API is a materially better fit for a user-started Book Transcript than the mechanisms LAABS currently relies on.** The package wraps Apple's new `BGContinuedProcessingTask`, which is specifically designed for long-running, user-initiated work that starts in the foreground and continues if the app is backgrounded. Apple explicitly lists intensive CPU processing as supported and describes workloads taking "minutes or more." It therefore addresses the current failure mode where transcription freezes after playback stops and the screen is locked.

This is not a longer `UIApplication.beginBackgroundTask` assertion. That older assertion remains suitable for the current short SQLite flush, not for keeping a whole ASR job alive. A continued-processing task also differs from the app's existing `BGProcessingTask`: it begins from the user's foreground action and may continue immediately, instead of waiting for an opportunistic charger/idle window.

The recommendation is to **prototype the Apple primitive for manually started Book Transcripts on a real device**, preserving the existing watermark/resume and `BGProcessingTask` paths as recovery/fallback. The package is a useful accelerator, but version `0.1.0` is very new and has an expiration-completion detail that should be clarified or patched before shipping. Given that LAABS already owns the relevant Swift coordinator and Expo config plugin, implementing `BGContinuedProcessingTask` directly is also a credible and possibly lower-risk choice.

For an individual Clip Transcription, the benefit depends on duration. A continued task is appropriate only when recognition is expected to take long enough to warrant persistent system UI; an Apple DTS engineer advises that work tied to this API should generally take at least 20–30 seconds, otherwise `beginBackgroundTask` is the better fit. "All clips" text export does no ASR, so this module offers it no execution benefit.

## What LAABS does today

| Situation | Current behavior | Consequence |
| --- | --- | --- |
| Book Transcript while audio is playing | The legitimate `audio` background mode keeps the process running; the screen may lock. | Already works. A continued task mainly adds correct task semantics, visible progress/cancel UI, and protection if playback later stops. |
| Book Transcript with no playback, app foreground | `expo-keep-awake` keeps the screen on. | Works only while the app stays foregrounded. |
| Playback stops after the phone is already locked/backgrounded | A keep-awake request cannot wake a backgrounded app; the code documents that transcription freezes until foregrounded. See `src/transcription/transcription-wakefulness.ts:70-84`. | This is the gap `BGContinuedProcessingTask` directly closes. |
| App enters background | LAABS takes `UIApplication.beginBackgroundTask` only long enough to settle pending SQLite writes, then ends it. See `src/native/book-transcriber/BookTranscriber.swift:593-627`. | Correct cleanup behavior, not a long-running ASR lease. |
| Deferred background work | LAABS schedules `BGProcessingTask` no earlier than 15 minutes, requires external power, and relies on opportunistic scheduling. See `src/native/book-transcriber/BookTranscriptionBackgroundTask.swift:37-44,126-150`. | Useful overnight/resume path, but not immediate. |
| Cold/terminated process | The current coordinator deliberately declines a granted `BGProcessingTask` until the JS orchestrator is ready. See `src/native/book-transcriber/BookTranscriptionBackgroundTask.swift:16-28,159-180`. | Existing background processing only helps a process that remains alive-but-suspended. |

The Book Transcript pipeline is already well shaped for expiration: it persists batches and a track-relative resume watermark incrementally, cancels the native analyzer, and settles queued writes. That durability should remain authoritative regardless of which OS execution lease is active.

## Why the continued-processing API is better

Apple describes `BGContinuedProcessingTaskRequest` as a foreground-submitted request that starts processing immediately if possible and continues if the person backgrounds the app. Apple's long-running-task guide says continued tasks can run "minutes or more" and can perform intensive CPU work in the background; its examples include media export and image processing. Those semantics fit local `SpeechAnalyzer` transcription closely. [BGContinuedProcessingTaskRequest](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest), [Performing long-running tasks on iOS and iPadOS](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados)

The current `beginBackgroundTask` API only grants finite extra time to finish critical work during the foreground-to-background transition. Apple recommends it for completing a save or closing resources, warns that the expiration handler may run when time is depleted, and may terminate an app that fails to end the assertion. That matches LAABS's short flush use, not a 25–90 minute book transcription. [Extending your app's background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time), [Choosing Background Strategies for Your App](https://developer.apple.com/documentation/BackgroundTasks/choosing-background-strategies-for-your-app)

The current `BGProcessingTask` serves a different goal: the system chooses a suitable future launch time. LAABS further requires power and sets a 15-minute earliest-begin floor. By contrast, a continued task is submitted at the user's foreground action and either queues to begin as soon as possible or can use the `fail` strategy when immediate execution is required. [Apple's WWDC25 “Finish tasks in the background”](https://developer.apple.com/videos/play/wwdc2025/227/), [submission strategies](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest/submissionstrategy)

The system shows continued-task progress in a Live Activity and lets the user cancel. Progress is operationally important: Apple may terminate tasks abruptly under resource pressure and prioritizes termination of tasks making minimal or no progress. LAABS already has file and whole-book progress that can feed this API. [BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)

## Limits that remain

- **No unlimited-runtime guarantee.** Apple publishes no fixed maximum duration. The system can expire a task because of runtime conditions, and stalled progress makes expiration more likely. Cancellation and expiration must stop `SpeechAnalyzer`, flush durable progress, and release the task promptly. [BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)
- **Foreground, explicit user action is mandatory.** Apple says submission must result from a person's action such as tapping a button. Automatic maintenance, backup, or preference-driven work may be canceled. The direct Start Transcription button fits; a watcher that starts transcription later after a download is more questionable unless the continued task is submitted as part of the original explicit “download and transcribe” action. [Apple's WWDC25 session](https://developer.apple.com/videos/play/wwdc2025/227/)
- **Force-quit still wins.** Apple cancels continued tasks when the user removes the app from the app switcher, without delivering cancellation to the app. The package also reports `supportsReattach: false` on iOS. LAABS must retain its watermark/resume behavior. [Apple's long-running-task guide](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados), [package README](https://github.com/mahdidavoodi7/react-native-continued-task#reconciling-after-a-silent-kill)
- **The user can cancel from system UI.** On iOS, user cancellation and system expiration both arrive through the same argument-less expiration handler, so product behavior must treat both as “stop safely and preserve partial work.” [Apple's long-running-task guide](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados), [package README](https://github.com/mahdidavoodi7/react-native-continued-task#ios-cannot-tell-you-the-user-cancelled)
- **Real-device verification is required.** The package says the continued task is unavailable in the simulator. Its published device run validates submission, progress UI, cancellation, stalled-task expiration, and force-quit reconciliation on one iPhone/iOS 26.6.1, but does not validate a long `SpeechAnalyzer` workload. [package testing notes](https://github.com/mahdidavoodi7/react-native-continued-task#testing), [device QA report](https://github.com/mahdidavoodi7/react-native-continued-task/blob/main/docs/device-qa-runs/2026-09-01-ios-26.6.1.md)

## Package-specific assessment

The package provides useful plumbing: an Expo config plugin, typed submit errors, progress/title updates, stop listeners, persisted task records, and Android WorkManager foreground-service support. It is version `0.1.0`, released 2026-09-01, and its repository currently contains a single release's worth of history. LAABS already depends on `react-native-nitro-modules`, which reduces adoption overhead, but LAABS has `^0.35.0` while this package was generated/tested with Nitro `0.37.1`; the package declares a wildcard peer range, so compile/runtime compatibility needs to be proven rather than assumed. [package metadata](https://github.com/mahdidavoodi7/react-native-continued-task/blob/main/package.json), [changelog](https://github.com/mahdidavoodi7/react-native-continued-task/blob/main/CHANGELOG.md)

One source-level concern should be resolved before shipping. Apple's documentation says failing to call `setTaskCompleted(success:)` before the task expires may lead to termination, and Apple's sample uses expiration to stop work before the normal completion path marks the task complete. In package `0.1.0`, the expiration handler calls `stop()`, which sets state to `stopped` and clears the native task; a later `complete()` then exits early because it accepts only `pending` or `running`. Thus the expired task does not appear to receive `setTaskCompleted`. This may be tolerated by the OS after expiration, but it is not the completion pattern Apple documents. Verify with the maintainer or patch/fork it, then run forced-expiration tests with the ASR cancellation-and-flush path. [Apple `setTaskCompleted`](https://developer.apple.com/documentation/backgroundtasks/bgtask/settaskcompleted(success:)), [package `HybridContinuedTask.swift`](https://github.com/mahdidavoodi7/react-native-continued-task/blob/main/ios/HybridContinuedTask.swift#L108-L249)

Because LAABS already has a native `BookTranscriptionBackgroundTaskCoordinator`, a direct implementation would avoid that dependency risk while reusing almost all existing lifecycle behavior. The package's largest unique value to this app is therefore convenience and cross-platform normalization, not access to a capability LAABS could not implement itself.

## One clip versus Book Transcript versus all clips

| Flow | Recommendation |
| --- | --- |
| User taps Start for a Book Transcript | Best candidate. Submit a continued task synchronously from the foreground action, bind its progress to the existing durable watermark/whole-book progress, cancel and flush on stop, and complete it on success/failure. Keep `BGProcessingTask` as a later charger/idle recovery route. |
| Individual Clip Transcription fallback | Potentially useful for long clips—the app permits clips up to one hour and the native path uses `SFSpeechURLRecognitionRequest`—but likely excessive for a short recognition that finishes in under roughly 20–30 seconds. A short `beginBackgroundTask` wrapper would be simpler for those. See `src/components/bookComponents/clip-timing.ts:1-3` and `src/native/clip-transcriber/ClipTranscriber.swift:113-189`. [Apple DTS guidance](https://developer.apple.com/forums/thread/807370) |
| Export all clips | No benefit. That flow reads already-persisted Book Transcript segments and does not launch on-device ASR. |

## Suggested device spike

1. Wrap only a manually started Book Transcript in a continued task; do not remove the existing wake-lock, audio-mode, or `BGProcessingTask` paths yet.
2. Report progress on every durable segment/watermark update, not only at file boundaries.
3. On expiration/cancel: stop the analyzer, settle the SQLite write tail, then call `setTaskCompleted`; preserve the transcript as resumable.
4. Test a release build on a physical iOS 26 device in four cases: screen locks with no playback, playback stops after lock, Control Center cancellation, and simulated/system expiration. Run a 30–90 minute wall-clock transcription, because the package's upstream QA does not cover that duration or SpeechAnalyzer.
5. Test force-quit and relaunch to confirm the persisted watermark remains the sole recovery source.

Android is not currently a Book Transcript platform in LAABS. If Android ASR is added later, the package's long-running WorkManager foreground worker is useful, but it is subject to Android foreground-service and JobScheduler rules. Android documents local ML crunching as an intended long-running-worker use, Android 15 caps `dataSync` and `mediaProcessing` foreground services at six hours per 24 hours, and Android 16 applies job quota to WorkManager long-running workers. Use the `mediaProcessing` service type for media ASR rather than the package's default `dataSync`, and verify Play-policy fit. [Android long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running), [foreground-service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)
