# Read-Along Clip Selections Produce Ordinary Clip Bookmarks

A Clip Selection in Read-Along saves an ordinary Clip Bookmark — a Clip Range and a Bookmark Title — and stores none of the selected transcript text. The transcript is already durable and time-aligned, so the words inside a Clip Range are re-derivable from the Book Transcript; snapshotting them onto the bookmark would add a second copy that drifts and a field that only one creation path ever writes.

## Considered Options

- **Snapshot the text into Local Note.** Free plumbing — it would appear in Bookmark Detail and Bookmark Backup Export today. Rejected because Local Note is a user-owned field, and pre-filling it with machine-generated text squats in it.
- **Snapshot the text into a new record field.** Survives transcript deletion and leaves Local Note alone. Rejected as a new structure carrying a second copy of text that can disagree with the transcript it came from.
- **Store nothing and never render transcript text for a bookmark.** Rejected only in that it forecloses future surfaces; the write path is identical to what we chose.

## Consequences

- CONTEXT.md already records that a Book Transcript exists only while its audiobook has Downloaded Audio Assets. Deleting the download therefore strips the recoverable words from every clip made this way. The required Bookmark Title is the mitigation: it is a stored, user-written string, which is why the save flow asks for a name rather than auto-titling.
- Creation routes through the existing Add Bookmark Sheet, seeded with `libraryItemId`, start, end and `kind=clip`, rather than calling `addBookmark` directly. One save path keeps ADR 0001's Local Bookmark Record invariants from drifting, and the sheet's existing clip toggle lets a reader demote a selection to a Point Bookmark for free.
- `addBookmark` infers record identity from `(libraryItemId, startTimeSeconds)` when no `localBookmarkId` is passed. At the player a collision is rare; in Read-Along it is the normal case, because clipping one sentence and then clipping that sentence plus the next four floor to the same start second. Saving therefore asks **Replace** (threading the existing `localBookmarkId`) or **Save as new** (which needs a force-new path in the store) instead of silently overwriting a title and note the user wrote. Fixing the root cause — removing start-time identity inference everywhere — was rejected as a much wider change touching the reconcile and delete paths.
- **Save as new produces an Unmatched Bookmark, by construction.** Audiobookshelf keys a Server Bookmark by time, so two local records sharing a start second cannot both have one. On the next reconcile, `findLocalBookmarkByServerTime` matches the older record and the newer one is marked `unmatched`; its pending-create is deduplicated by `toPendingBookmarkId`, which is keyed by the same second. The duplicate keeps its Clip Range, Bookmark Title and Local Note — ADR 0001's Local Bookmark Record ownership is exactly what makes this survivable — and ADR 0002 already allows Clip Export for an Unmatched Bookmark. No data is lost; the cost is that the second clip's title never reaches the server.
- A Clip Range is derived by flooring the first segment's start to the second and ceiling the last segment's end. The outward rounding is the padding; no lead-in constant is introduced, because a fixed pad drags neighbouring words into tightly-packed dialogue and reads as a bug in a feature that promises exact sentences. A selection under `MIN_CLIP_DURATION_SECONDS` extends its end to reach the floor, since that minimum is an audio-artifact constraint rather than a semantic one.
- A Clip Selection may cross section boundaries. A section is only a track boundary when `sourceStructure` is `files`, so a blanket rule would be wrong on chapter-structured books; per ADR 0002, telling the user that a cross-track clip cannot be exported stays Bookmark Detail's job and does not leak download or export state into a reading surface.
- Read-Along gains a Bookmark Gutter rather than a bookmark list — a margin lane is the only marker that collides with none of the active-segment tint, the active-word treatment or the selection tint, and it shows a clip's extent for free.
- Selection state and per-row gutter markers live in the reader's own state and extend the segment item's memo comparator, which its doc comment describes as load-bearing. The exemption is deliberate and must stay documented there: that contract exists to keep *playback-frequency* state out of the screen, and both of these change at user frequency. The comparator and props moved to `src/read-along/read-along-segment-props.ts` so the contract could be pinned by unit tests — importing the component pulls in Reanimated's native module.
- **The contract's stable-handler clause is the sharp edge.** The comparator ignores handler identity, so a row whose other props are unchanged keeps whichever closure it last rendered with. The first implementation closed the tap handler over the live selection and the bug was immediate: the first tap after a long-press seeked instead of extending (that row had not re-rendered), and a tap after a cancel extended from the cancelled selection's anchor. The reader therefore keeps every gesture handler permanently stable and reads selection and transcript state through refs, with `setSelection` writing its ref synchronously so a tap immediately after a long-press sees the new selection.
