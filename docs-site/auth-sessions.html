Auth, Sessions & Libraries

The app remembers multiple sign-ins and switches between them safely. The trick is separating who owns your listening state (a durable identity) from how you reconnect (a saved server + username) — and never tearing down durable data on a failed switch.

🪪
Two ideas you must not conflate

Remembered User Session is keyed by the Audiobookshelf User Identity (the server's user UUID) and owns all durable local state — bookmarks, progress, rate, position. Session Entry Option is just a way to restore a session (serverUrl + username). Several Entry Options (LAN URL, public URL) can restore the same identity. The server endpoint is for API calls only — never for local-state identity. (ADR-0015 / 0020)

One entry path for sign-in and switching

There is no loginWithPassword or restoreSession action. Everything — first sign-in, switching users, re-entering after an error — goes through one navigation-free function, enterUserSession(request), which runs five phases in a fixed order so a failed or interrupted entry never leaves you worse off than before you tried.

The result is a SessionEntryResolution — activate, needsLibrarySelection, noLibraries, or failed. Because enterUserSession is navigation-free, screens call useApplySessionEntryResolution() to turn that outcome into routing. Screens never hand-sequence authenticate/commit/resolve themselves.

🛟
Crossing the boundary only sheds live state

Same identity (switching endpoints) → tear down only streaming playback. Different identity → end playback (after capturing a Progress Sync Intent), clear Library Activation, and clear the session-scoped query cache. It never touches durable, identity-scoped data: bookmarks, progress intents, and downloads always survive.

Access Mode is the only thing routing branches on

Raw AuthStatus (hydrating / anonymous / authenticated / offlineOnly) plus stored state is collapsed by selectAccessMode into a single Access Mode. Root routing reads that, not status.

Resolution → Selection → Activation

After entry (or whenever an authenticated session has no Active Library), libraries resolve in three steps:

StepWhat it is
ResolutionZero / one / many libraries? Zero → browsing unavailable. One → may auto-activate. Many → user must select. (ADR-0004)
SelectionThe user's choice of which library becomes active (Home menu, or the /library-picker sheet).
ActivationPrepare the chosen library before committing it as active. Needs userServerState; catalog is not part of activation. (ADR-0009)
⚠️
Activation invariants

Never commit a new Active Library before activation succeeds; never let a half-loaded Home become interactive; never let playlist loading block activation; never let the picker sheet own the commit (it only captures intent and hands off to the one shared activation command).

Listening State Owner

Many surfaces need "which identity owns this book's local state right now." That's the Listening State Owner: the signed-in/remembered identity if present, otherwise the book's Downloaded Asset Owner. Resolve it in one place — useResolvedListeningOwnerKey() (components) or resolveListeningOwnerKey() (services). Don't re-spell activeLibraryUserKey ?? storedUserId ?? downloadOwner inline.

Storage, tokens, and logout

  • SecureStore holds per-session secrets, keyed abs.session.<key>.<password|accessToken|refreshToken>. No global credential slot.
  • MMKV holds the remembered-sessions snapshot (abs.sessions) and the small Zustand auth slice (active library + stored user id).
  • Token refresh (refreshSession): valid token returns as-is; else POST /auth/refresh, then stored-password re-login; if both fail, clear tokens, flag needsAttention, drop to anonymous/offlineOnly.
  • API calls go through absClient → authFetch, which injects Bearer, refreshes when needed, and retries once on 401.
  • Logout snapshots progress, ends playback, clears caches + tokens + credentials for every Entry Option of that identity, and routes to Login — but downloads, local bookmarks, and progress intents stay on disk. (ADR-0010/0011)
