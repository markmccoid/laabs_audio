Progress & Sync

Listening position is kept durable on the device before the app ever asks the server to accept it. The hard parts are choosing where to resume and making sure a stale server snapshot can never drag your position backward.

🧷
Guiding principle

Local evidence is trusted first. Every meaningful moment writes a durable Progress Sync Intent locally; remote sync is something that happens after, and is allowed to fail without losing data.

Four storage layers

Progress passes through four places, each with a different job:

LayerRole
Playback store (Zustand)High-frequency live ticks during playback. Not persisted as truth.
React Query cache (+MMKV)userServerState — the progress the UI reads. Updated optimistically even when the server is unreachable.
Offline pending queuependingProgressByUser in deviceBooksStore — durable intents waiting to reach the server.
Audiobookshelf serverThe eventual source of truth, reconciled carefully on the way in.

When and how it syncs

playerService.syncProgress() runs at sync points and picks a strategy. The interval tick is opportunistic; pause, seek, stop, book switch, background, interruption, and finish are durable moments that always leave a local intent first.

Two flush rules keep the queue honest:

  • Latest-wins, one per book. A new write replaces the older queued value for that libraryItemId; entries are user-scoped and survive restarts.
  • Oldest-first flush. On reconnect (online + authenticated), useAuthBootstrap flushes in order — progress, then bookmark creates, then bookmark deletes — sending queued progress sorted by updatedAt ascending, removing only successes and keeping failures for retry.

Choosing where to resume

When a book loads, Resume Resolution picks the listening position from a ranked set of candidates. The same logic also seeds the displayed position early, before streamed metadata and native audio are ready, so the scrubber never starts at zero.

  1. Fresh server progress fetched during load.
  2. userServerState cache (including older persisted shapes).
  3. A pending Progress Sync Intent for the book.
  4. Persisted playback-store position, if nothing stronger exists.
⛔
Fresh server progress can advance, never rewind

A full-snapshot refresh from the server must not move a book's position backward or override newer local evidence. The reconciler also preserves progress for books missing from a snapshot rather than treating "absent" as "reset to zero." This is why a resume point can be correct even when the server cache looked stale.

Intents, identity, and edge cases

  • Explicit finished / unread is authoritative user intent and isn't second-guessed by automatic samples.
  • Automatic zero-position samples must not erase meaningful position evidence (native setup briefly emits 0).
  • In-flight safety: a successful sync clears only the intent it synced (or an older one for the same book + user scope). A newer intent created mid-sync stays pending.
  • Identity-scoped: a downloaded book whose session "needs sign-in" keeps recording intents under its remembered user scope; they flush only when that same session is restored. A signed-out "required sign-in" state doesn't permit playback, so it creates no new intents.
  • Unmatched intents: a book missing during flush becomes an Unmatched Progress Sync Intent rather than retrying forever.
