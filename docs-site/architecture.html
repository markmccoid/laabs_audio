Architecture

The big picture: where every piece of data lives, who owns it, and how the app boots from a cold start to a usable Home screen.

🧱
The core idea

State is split into three buckets by ownership, not by feature. Knowing which bucket a piece of data belongs to tells you where to read it, how it's persisted, and what's allowed to invalidate it.

Where data lives

The app talks to a self-hosted Audiobookshelf (ABS) server, but it never depends on the network for a responsive UI. Server data is projected locally into two very different stores, and the device keeps a third store of things the server never knows about.

The three buckets in detail

① SQLite shadow database — the Library Catalog read model

Owned by the server, projected locally (ADR-0017/0019). It holds the catalog projection columns plus a JSON summary, a full-text search index, genre/tag facet rows, server progress snapshots, favorites, bookmarks, and pending progress intents. It's read through sqliteSearchRepository and sqliteHomeRepository, and refreshed in the background by the Library Refresh Coordinator. Crucially, the full catalog never enters React Query or MMKV — that's what keeps startup cheap. See Data & SQLite for the module map and schema.

② React Query + MMKV — user server state

Also owned by the server, but small and user-specific: progress / currentTime / isFinished, server bookmarks, and playlist contents. These queries persist to MMKV across launches, but only if they opt in with meta: { persist: true } — and SQLite-prefixed keys are never persisted. Defaults: staleTime 5 min, gcTime Infinity.

③ Zustand — device client state

Things the server doesn't know about and shouldn't: downloaded file URIs and download progress, custom local covers, the offline progress/bookmark/playlist queues, playlist shelf projections, per-user-book playback rate, and the live high-frequency playback state. Split across device-books-store (durable device data) and playback-store (live player state).

Reads, writes, and invalidation

SQLite-backed query keys carry a shape segment so invalidation stays surgical:

ShapeCoversInvalidated by
"overlay"Search result sets, Home projectionfavorite/progress mutations → invalidateSqliteOverlayProjections
"catalog"Item summariesonly the refresh coordinator → invalidateAllSqliteProjections
⚠️
Never invalidate a raw ["sqlite"] prefix

Go through src/query/sqlite-invalidation.ts. A blanket prefix invalidation throws away expensive catalog summaries along with the cheap overlay rows.

Playback write-through

During playback, high-frequency ticks stay in playbackStore. At sync points the service tries a server sync; whether or not that succeeds, it mirrors the latest progress into the React Query user cache and the SQLite overlay projection, then invalidates overlay-shaped keys — so the persisted cache is updated without an extra fetch, and loadBook can resume instantly from cache. (Full rules on Progress & Sync.)

Cold start to first Home

Startup is gated on as little as possible. The strict gate is auth hydration; everything expensive (catalog refresh, warmups, sync flushes) is pushed behind first content and user interactions.

⏱️
Measuring it

src/utils/dev-startup-tracing.ts prints one compact line per run, e.g. [startup] Home Shelf Display in 1509ms | auth 53ms | secureStore 50/51ms | queryRestore 49ms | homeHook 334ms | renderLayout 548ms. The usual suspects are SecureStore reads (the hydration gate) and the synchronous JSON.parse of the persisted cache.
