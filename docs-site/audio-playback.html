Audio & Playback

How a tap on Play becomes sound — from the UI, through the orchestration layer, across the engine adapter, to the native player and back as progress events.

🧭
The one rule

UI never talks to the audio library directly. All actions go through playerService, and all state comes from usePlaybackStore. Everything below is in service of keeping that boundary clean.

The request path

There are four layers between a button and the speaker. The top three are ours; the bottom one is the swappable native library (react-native-audio-pro). Commands flow down; progress and state events flow back up and land in a Zustand store that the UI subscribes to.

A mental model first

Two ideas unlock the rest of the system:

  • Book position vs. track position. A book is a queue of audio files. Book position is absolute time across the whole audiobook; track position is time within the current file. The app thinks in book time and converts down to tracks only at the engine edge.
  • Source is just a URI. Every track resolves to a source.uri that is either remote (https://) or local (file://). The native player only accepts those two schemes — everything else in the app exists to produce the right URI and seek to the right book position.

Three ways a book loads

playerService.loadBook(libraryItemId) is the single entry point, but it resolves its source in a deliberate order. Downloaded files always win.

The practical outcomes the UI relies on:

SituationBehavior
Offline + downloadedPlays from local file:// files.
Offline + not downloadedPlay is disabled in book controls.
Online + downloadedStill prefers the downloaded files as the source.

(There is also a loadLocalFile() demo path used by the Home screen — a one-item local queue — useful for verifying the engine in isolation.)

Why the adapter exists

audio-engine.ts is a deliberately small interface so the native library can be swapped without touching the rest of the app. If react-native-audio-pro is ever replaced, only this file changes. 

// the entire surface the app depends on
interface AudioEngine {
  load, play, pause, seek, setRate,
  getPositionMs, getDurationMs, unload,
  setEvents // progress + state callbacks
}
🔌
Engine-swap safety

The bigger migration risk isn't this interface — it's ambient audio, which currently calls AudioPro directly in ambient-service.ts and is not behind the adapter. A new engine needs its own plan for that channel.

Seeking across a multi-file book

seekTo(positionMs) and skipBy(seconds) operate on book position, not track position. When a seek crosses a file boundary, the service finds the correct track and loads it automatically. Chapter positions are likewise stored as absolute book time, so nextChapter() / previousChapter() just resolve to a book position and call seekTo — track switching is handled for you. This is the only safe way to move around multi-track audiobooks.

The Book Controls state machine

Each book view tracks its own UI state, independent of whatever book is globally active in the player. That's what lets a detail screen show a spinner the instant you press play, before any metadata or queue exists.

Two guardrails worth knowing:

  • Confirmed PLAYING. The store only flips to playing after the native engine reports PLAYING for the target track — not optimistically on the play call.
  • Provisional streamed sessions. On streamed autoplay, the session stays provisional until playback actually starts within a startup budget. If it doesn't, the service unloads, closes the session best-effort, shows a poor-connection toast, and returns to not-loaded.

Who owns playback rate

Rate lives in two places, on purpose:

  • Active rate → playbackStore.rate (the live value driving the engine).
  • Per-book rate → deviceBooksStore, scoped by userKey + libraryItemId (defaults to 1.0).

setRate() is the only write path and updates both. On the next load of that book the stored rate is restored, and play() re-applies it after native playback starts — because some native replay paths momentarily reset speed to 1.0×.

Progress & sync, in brief

The engine emits progress once per second. playerService writes through to the local cache immediately and syncs to the server on a schedule — every 5 minutes during playback, on pause, on explicit seek, and on the background/termination path. Anything that can't sync (offline, unauthenticated, or a thrown call) is queued per book and flushed on reconnect.

Common pitfalls

SymptomCause / fix
No audio on iOSThe native player only accepts file:// or https:// URLs. Check track.url.
Missing artworkArtwork is validated; the app supplies a default icon when a URL is rejected.
Queue missing after reloadPersistence is partial (only libraryItemId, currentTrackIndex, positionMs, rate). Always call loadBook / loadLocalFile to rebuild.
