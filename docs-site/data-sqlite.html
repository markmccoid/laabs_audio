Data & SQLite

A local SQLite "shadow" read model projects the Audiobookshelf catalog onto the device so search and Home stay fast even on very large libraries — the cost of a read scales with the viewport, not the library.

🎯
Why this exists

(ADR-0017 / 0019) Holding a full catalog in React Query/MMKV made startup parse a huge JSON blob and made every search walk the whole library in JS. The shadow DB moves catalog data into queryable SQLite, keeps the persisted snapshot tiny, and pushes matching/sorting into SQL.

The read path

Search and Home read through repositories, never the database directly. Production reads are ids-first: a single scan returns ordered Audiobook Identities (plus the user's favorite/finished id sets), and display summaries are resolved in viewport-sized chunks as rows approach the screen.

Four conventions that keep it fast and correct

  • Scope is read in exactly one place. Global auth state is only touched inside requireActiveLibraryContext. Long operations capture their scope and pass it back in; the binder throws on mismatch, so an Active Library switch mid-refresh fails loudly instead of writing rows under the wrong library.
  • All matching lives in search-expression.ts. Text (FTS), genre/tag operators, author/narrator, Favorite/Finished filters, and sort are realized by one pure builder. Adding a filter is a one-place change that the production reader, the diagnostic sampler, and the filter sheet all inherit.
  • Ids first, summaries lazy. Don't add summary parsing back into the result-set query — cost must scale with the viewport, not the library.
  • Bulk writes are chunked. 50-row multi-row VALUES statements with a frame yield between chunks (bulkUpsertRows); large IN (...) id lists chunk at 400. No per-row awaited INSERT loops.
⚠️
Invalidate only through the helper

Keys carry a shape segment — "overlay" (refetch after favorite/progress mutations) vs "catalog" (survive overlay mutations). Mutation sites call invalidateSqliteOverlayProjections; only the refresh coordinator calls invalidateAllSqliteProjections. Never invalidate a raw ["sqlite"] prefix.

The library_refresh_runs table is what makes paged refresh safe: a run is only allowed to soft-delete "not seen" rows after it completes, so a partial/failed refresh can never wipe the catalog.

How the catalog gets filled

Refresh data comes from the ABS API layer (see the API map). The catalog refresh pages metadata via libraryItemsApi.getItemsPage(); the overlay refresh pulls user state via meApi.getUserServerState(). The two are separate on purpose — catalog metadata is large and shared, user state is small and per-session.

🔑
The persist invariant

React Query options are shared per key. If any observer of a persisted key omits meta:{persist:true} — even a disabled subscription hook — it can knock that query out of the next save cycle and cause a startup cache miss. All observers of a persisted key must carry the same opt-in.
